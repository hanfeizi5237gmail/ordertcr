# 当前 order-mapping 准确率下降场景分析

分析日期：2026-11-08。范围：当前 skill 指令、确定性执行器和已有 v5 证据；补充12组只读解析诊断、同历史数据 profile 消融及一个合成品牌防护反例。不修改 skill、profile、运行状态或 original；不连接外部系统。诊断数据见 [accuracy_risk_evidence.json](accuracy_risk_evidence.json)。

## 结论

最大的退化因素是公司偏好缺失或使用范围不对、原始聊天语法超出当前解析器、公司/日期/修订上下文缺失，以及宿主 Agent 未完成语义复核。包装计价依据不足会降低自动完成率；主动留空和标异常属于安全行为，不能直接视作选品错误。当前96.21%只对应同三站历史参考样本的132项可核人工SKU，不代表全159事件的整单自动完成率，也不代表新订单准确率。

v5 seed 20261108 的 `single_station_random_split / profile_only` 原始逐项记录中：

|指标|数量|含义|
|---|---:|---|
|当前目录可核人工SKU一致|127/132，96.21%|身份一致率，带公司历史profile|
|全对齐事件SKU一致覆盖|127/155，81.94%|原人工可核身份一致数除以全部对齐事件|
|全聊天事件SKU一致覆盖|127/159，79.87%|不是其余32项全部错误，包含缺少目录真值等项目|
|商品身份已选定|134/159|`product_status=matched`，不保证数量/日期已解决|
|数量换算已确定|103/159|`quantity_status=matched`，不代表实际配送数量|
|整行状态matched|94/159，59.12%|该次回放数量、日期、重复等未决项未阻断计金额的行数；不是独立整行正确率|
|仍待处理的行|65/159|金额留空，不能当完整应收金额|

## 一、公司profile缺失、失效或错用

现有简称与采购习惯大量依赖公司profile。例如“土豆”“干豆腐”“一品鲜酱油”的原文没有完整目录商品信息，公司偏好承担SKU消歧。

只读消融在同159历史事件上直接调用 `match_item`，不注入逐项决策、不调用Agent语义复核：

|站点|带当前profile|不带profile|
|---|---:|---:|
|松北大道|40/44|11/44|
|星月|34/35|11/35|
|学院路|53/53|16/53|
|总计|127/132，96.21%|38/132，28.79%|

该结果仅量化确定性匹配器对profile的依赖，不能称为完整skill在新公司的28.79%准确率。完整skill要求Agent继续主动语义核对。

实际触发场景包括：仅复制通用skill而未迁移私有profile；公司ID改变；目录更新后profile版本失效；同义单位超出别名`request_units`范围；采购品牌/包装习惯改变而目录版本未变。前几项通常安全退化为待人工；习惯改变且旧profile仍有效则可能选错。

依据：`profiles.py:23-64,93-105`；`matching.py:143-168`；`references/portability.md:16`。本批profile与人工真值来自同一批历史材料，存在拟合边界。

## 二、聊天语法超出当前解析能力

以下为本次直接调用当前 `parse_chat` 的结果，未经过Agent修复：

|输入|实际解析|影响|
|---|---|---|
|土豆5斤，白菜3斤|正确分为两项|当前支持的常规分隔|
|土豆5斤/白菜3斤|一项，品名为“土豆5斤/白菜”，数量3斤|商品事件合并|
|土豆5斤白菜3斤|一项，品名为“土豆5斤白菜”，数量3斤|第一项需求被吞入品名|
|鸡腿2袋（每袋5斤）|品名“鸡腿2袋（每袋”，数量5斤|把包装内重量作为下单数量|
|食盐1/2袋|品名“食盐1/”，数量2袋|分数被误读|
|鸡蛋半筐|数量和单位均缺失|中文半数量未支持|
|青椒、红椒各5斤|青椒无数量；红椒品名含“各”|共享数量未展开|
|5斤土豆|整句被视作品名，缺数量|前置数量未支持|
|明天要的菜 / 土豆5斤|日期说明被当商品，后项无日期上下文|相对日期未结构化|
|11.3 / 土豆5斤|11.3被当商品，后项无日期上下文|点号日期未识别|
|土豆算了|普通品名，event为空|口语取消未识别|
|星月站：土豆5斤|站点进入品名，target_station为空|普通公司前缀未路由|

根因是当前数量识别选最右侧符合格式的数字，分隔符采用有限规则，日期和事件识别也采用有限表达式。若Agent直接接受脚本解析结果而不逐项核对原文，这些问题会进入后续匹配；Decimal只能保证基于输入数值的运算，无法纠正已经抽取错误的数量。

依据：`parsing.py:7-13,61-99,119-129`。

## 三、跨站混聊及公司归属缺失

生产处理入口一次只处理一个公司/日期批次。当前只在`target_station`被解析出来时检查原文明示站点与批次公司是否冲突；普通“星月站：”前缀并未由解析器转为`target_station`。如果人工或Agent把混合聊天错误归入某一个合法公司，该公司的profile可能被应用到其他站点需求。

v5跨站正向回放利用manifest中的可信来源公司分区；不分区负向场景在**评估脚本**中直接清空`assigned`以停止CLI处理。因此上一轮“不分区通过”的准确含义是评估包装层拒绝处理，尚未证明skill主入口能够自动发现任意真实混公司文本。反事实回放只证明指定目标profile生效且没有历史决策注入，目标公司没有人工SKU真值，也未要求所有错误公司事件自动识别为错误归属。

依据：`workflow.py:292-296,340-342`；`v5_replay_audit.py:393-417,425-446`；`v5_validation.py:109-158`。

## 四、追加、改量、取消和重复依赖前后文

“再加这样的”“刚才的改成3斤”“不要了”“还是按原来的”“土豆算了”需要指向前单。执行器对一部分关键词、同批同名同量重复和“这样的”设待核，但没有自动完成跨批前驱关联和最终有效数量归并。

v5生成器将`antecedent_source_event_id`保持为空，并随机拆散事件；它验证事件原文保留，不验证修订关系的最终业务结果。原消息不丢失不能证明订单最终数量正确。重复消息分散到不同批次时，同批重复检测也无法替代跨批核对。

依据：`workflow.py:326,343-349`；`v5_simulation_generator.py:24-32,61-75,92-98,135-138`。

## 五、SKU约束、有限品牌词表及历史替代

现有5项人工SKU不一致为：下五花肉/精五花、玉米粒袋装/罐头、秋林/农大红肠、罗马/西生菜、鸡腿块/鸡肉块。这些项目存在真实的需求约束差异，不能将人工表中的替代全部注册为通用同义词。

代码层面，品牌防护采用有限词表；历史别名和逐项决策缺少覆盖所有部位、品种、鲜冻、加工、包装约束的统一机器校验。Agent提供`selection_basis`声明，并不等于执行器实际证明已筛选全部约束。

本次合成反例在仅含“牛肉”的虚构目录中故意登记“恒都牛肉→牛肉”的错误别名，当前匹配器返回`product_status=matched`且无问题代码。它证明词表外品牌可绕过当前防护，不表示在真实公司profile里发现了此错误。品牌出现在数量后备注等位置也需要Agent全文核对。

依据：`matching.py:15-26,143-168`；`profiles.py:39-49`；`workflow.py:201-225`。

## 六、缺少包装/实重依据降低整单自动完成率

“鲤鱼5条”“鸡蛋1筐”“肉1箱”不能自动转换成目录500g计价量；相同袋/包文字不证明所有商品包装净重相同。明确SKU后仍需独立核定换算。

v5 profile-only代表场景存在31条`quantity_conversion`问题、13条日期问题、2条重复事件问题、1条指代未决等，代码可同时给同一行多个问题，不能将问题数相加当独立失败行数。65行金额留空是安全结果，并不意味着65项商品都选错。不得为追求完整金额沿用人工旧实配量。

依据：`units.py:95-126`；`workflow.py:350-365`；本次诊断JSON中的`v5_profile_only_issue_counts`。

## 七、目录更新和跨宿主能力变化

新目录缺少旧SKU、同名新增规格或重命名会增加待核；目录更新使旧profile失效是保护机制，重新校准之前自动命中率可能下降。即使编号未变，包装关系、品种和价格层级改变也需要重新核对。没有接收到/注册新目录时，本地无法自动知道其他设备持有的新版本。

skill执行器不会自动调用模型。宿主未完整加载业务规则、未执行逐行语义选品、不能完整读取目录、缺Python/openpyxl、无原生Excel批注或未复读保存结果，都可能降低识别或交付质量。千问办公/WorkBuddy真实宿主效果尚无实测，不应外推本机成绩。

依据：`SKILL.md:13-19`；`profiles.py:93-105`；`references/portability.md:3-16`。

## 八、当前验证边界会掩盖部分退化

1. 两个seed重排同159个历史事件，没有增加独立新订单样本；原文不变，因此没有测新错字、新简称、规格数字嵌套或新的取消表达。
2. v5通过v4的`SEPARATORS`生成器，只在六种已支持的换行/逗号/顿号/分号间变化；未因此覆盖斜杠、无分隔等语法。
3. 原始事件和模拟事件字段来自同一个解析器，字段保持验证可证明不漂移，不能独立证明初始语义正确。
4. v5汇总的`representative_items`只取拆分场景；“所有场景稳定”的汇总实际只比较每个seed该代表场景。详细JSON记录了其他场景，但状态判定没有遍历全部场景逐项检查。
5. `status=verified`未强制纳入回放错误列表、人工工作簿差异、异常候选/批注等独立指标、反事实错误、不分区结果、每站门槛及实际前后SHA比较字段。本次详细回放记录为0错误，这项发现不否定已读到的127/132，但未来可能漏报退化。

依据：`v4_simulation_generator.py:23,32-55,100-128`；`v5_validation.py:40-41,60-67,202-239,245-249`。

## 建议处理优先级

1. 先强化解析：商品事件边界与规格内数字分离，覆盖分数/半数量/前置数量/共享数量/聊天头部。
2. 将公司归属校验和待人工状态放到正式处理入口；没有可信来源分区时拒绝直接应用某一公司的profile。
3. 补充跨消息修订关系和最终有效订单状态，不仅检测关键词。
4. 对别名/逐项决策统一校验品牌、部位、品种、鲜冻和包装；分离词表检查与Agent的证据审查。
5. 补齐v5汇总验收条件；增加新名称、新包装、新公司和不参与profile校准的新订单验证。

本轮仅完成分析及只读诊断，未实施上述修改。原始8文件SHA在本次诊断前后保持不变。真实新订单准确率、真实宿主执行、跨批事件最终结果和实际财务入账均未验证。
