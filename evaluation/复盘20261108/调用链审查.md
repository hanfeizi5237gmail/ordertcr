# 订单映射调用链审查（2026-11-08）

## 审查范围与结论

本次只读检查覆盖 `run-messages` 从 CLI 入口到聊天解析、目录/知识匹配、事件控制、订单与财务导出、批次台账和指纹审计的实际代码路径。未运行新测试，未修改生产代码、规则、测试或既有评测产物；本文件是当前实现的调用链复盘，不是新增设计。

直接结论：

1. **正常 `run-messages` 主链路没有正式的 Agent 语义判断调用。** `SKILL.md` 明确要求 Agent 主动做品牌、部位、鲜冻/熟制、加工、大小和包装审阅，但脚本没有模型、LLM、HTTP 或 MCP 调用，也没有在 `run-messages` 中产生语义决策。
2. **当前可执行主链路主要是确定性代码：正则解析、站点/日期路由、有限别名与知识选择器、目录名称/规格/约束匹配、单位换算、金额计算、编号、Excel 导出、原生批注和指纹台账。** `matching.py` 与 `expressions.py` 的“语义”是有限词表和正则表达式，不是模型推理。
3. **Agent decisions/candidate_reviews 是结构化 `run/process_batch` 的可选外部输入契约，不是内部 Agent。** `process_batch` 能校验并应用调用方传入的 `decisions` 和 `candidate_reviews`；`run-messages` 明确拒绝这两个字段，并且自己生成的内部批次不带它们。因此如果没有外部 Agent 先完成审阅并调用结构化 `run`，正常原文入口不会进入 Agent 语义审阅。

### 1.2 `run-messages` 输入边界与文件读取

`raw_messages.process_messages` 位于 `skills/order-mapping/scripts/order_mapping_core/raw_messages.py:140-291`：

## 2. 解析与事件控制路径

### 2.1 `parse_chat` 是正则/词表解析器

实际函数在 `skills/order-mapping/scripts/order_mapping_core/parsing.py:328-458`：

- `:8-17` 定义数值、单位、日期、分隔符、需求前缀等正则常量；`_NUM`、`_UNIT` 和 `_DATE` 是商品/数量分割的基础。
- `:19-46` 的 `_number` 将阿拉伯数字、中文数字、分数和“半”转为 Decimal 文本；错误数字被保留为 issue。
- `:76-108` 的 `_fragments` 依据标点、数量标记、要求/备注/规格等固定模式切片；`:111-168` 的 `_spaced_fragment` 依据“前一段已结束数量 + 后一段又出现数量”的正则边界拆分商品。
- `:176-325` 的 `_parse_item` 从右侧数量/单位正则提取 `name`、`quantity`、`unit`、`notes`，识别规格、加工词、追加、改量、重复和取消等固定表达，并保留来源 span。
- `:348-410` 只处理公司/站点/日期标题和上下文；`:411-457` 处理“各 N 单位”等固定句式并生成带 `line_id`、行号和字符区间的事件。

因此解析层可以稳定承担来源切片、数量/单位语法、公司/日期上下文和控制词识别；它不能理解未配置的新语义，也不会作模型式商品判断。

### 2.2 `run-messages` 的控制关系预匹配

当原文中出现改量/取消事件时，`raw_messages.py:195-268` 先做一次身份探针：

- `:195-217` 对每条事件按缓存键调用 `match_shared(probe, records, knowledge)` 或 `match_item(probe, records)`；控制词被从探针 `raw_text` 移除，但品牌、加工、否定等备注保留。
- `:218-225` 仅当匹配状态为 `matched` 且没有身份 issue 时记录当前目录身份 `(catalog, code)`。
- `:227-263` 按公司、日期、文本名和目录身份建立控制范围；未知或冲突身份进入 `unsafe_names/unsafe_identities`，不把目录身份全批次当普通重复键。
- `:268` 调用 `_resolve_events(items, identity_keys, unsafe_names, unsafe_identities, control_identities)`。
- `_resolve_events` 在 `raw_messages.py:40-138` 只在同公司、同日期、同一批次中处理显式追加、改量、取消、重复转发和未确认的同品关系；关系不唯一时状态置为 `pending`，数量和金额后续留空。

这部分也是确定性控制逻辑，不是 Agent 语义判断。

## 3. 从事件到匹配和导出的实际调用

### 3.1 `run-messages` 生成的内部批次

- `raw_messages.py:269-277` 按 `(routed_company, routed_date)` 分组，生成内部 `batch`，字段包括 `items`、`config`、`mode=order`、`date_policy=single`、`matching_mode` 等，然后调用 `workflow.process_batch(runtime_root, batch, output_root, base_dir=base)`。
- `raw_messages.py:277-281` 保存每个 manifest 的行索引，供最终事件结果回链到 Excel 行号。
- 关键边界：`:273-275` 生成的内部批次没有 `decisions` 和 `candidate_reviews`；这些字段不会从 `run-messages` 原始请求传入，因为 `:141-142` 已拒绝它们。
- `raw_messages.py:282` 调用 `merge_finance` 合并所有公司/日期批次；`:284-290` 写 `messages-result.json`，并明确记录 `runtime_inputs=raw_chat+confirmed_company_date+current_catalog+formal_knowledge`、`historical_decisions_loaded=False`。

### 3.2 `process_batch` 的匹配分派

`skills/order-mapping/scripts/order_mapping_core/workflow.py:295-540` 是结构化批次主流程：

- `:322-334` 获取并锁定当前目录，校验配置、公司和输入 items/chat_files。
- `:335-340` 读取可选 `decisions` 与 `candidate_reviews`，并校验其 `line_id` 必须属于本批 items；这只是输入合同校验，不会触发 Agent。
- `:367-373` 在 `shared` 或 `shared_with_company_contract` 模式加载正式知识、公司合同叠加和 `catalog_knowledge_audit`；当前公司合同为空时没有额外规则。
- `:377-384` 是逐项匹配实际分派：
  - 有 `decisions[line_id]` 时调用 `_decision`；
  - 否则有共享知识时调用 `match_shared`；
  - 否则调用 `match_item`；
  - 若有 `candidate_reviews[line_id]`，再调用 `_candidate_review`。
- `:385-432` 应用取消/日期/公司/重复/未解决指代等确定性控制，并在状态非 `matched` 时把 `amount`、`finance_amount` 置空。
- `:417-426` 只有 `matched` 行才用 `calculate` 计算单价和金额；`:430-432` 对任何未匹配行清空金额。

### 3.3 普通确定性匹配

#### `match_item`

`skills/order-mapping/scripts/order_mapping_core/matching.py:294-448`：

- `:294-302` 声明自动选择边界：只有明确别名或规范化后的当前目录精确名称可以选择 SKU；语义候选不会无确认升级为选中 SKU。
- `:307-335` 处理有限 `aliases`、别名目标 SKU、当前目录存在性、品牌冲突和过期别名。
- `:336-360` 对精确目录名/目录显式互见名称做规格可比性与最高价选择；规格不同、最高价并列时转 `ambiguous`。
- `:361-411` 调用 `_suggestions` 生成词面/后缀/模糊候选，并按类别、品牌、包装、规格等硬过滤；候选仅作为 `needs_review/ambiguous`，不自动选 SKU。
- `:412-448` 对已选目录行执行 `constraint_conflicts`、单位换算和加工履约检查；不满足约束或加工未证实时保留身份但清空计价数量/计价单位/金额相关字段。

#### `match_shared`

`skills/order-mapping/scripts/order_mapping_core/knowledge.py:227-376`：

- `:227-237` 按知识别名、条件和规则类型筛选适用规则，再调用 `match_item` 作为基础匹配。
- `:238-256` 处理“其他品牌/换包装”等未定要求并调用有限表达式规则；仍然不凭空替换品牌或包装。
- `:257-325` 依据知识选择器、已审阅候选/排除候选、当前目录候选池和属性冲突生成候选及证据。
- `:330-352` 在候选为空、出现未审阅目录名称、规则无自动适用候选、规则冲突、规格不同或最高价并列时保持待核。
- `:353-376` 只有唯一、同计价基础、满足条件且最高价唯一的候选，才把候选注入 `match_item` 的显式 SKU 别名并完成单位换算。

#### 有限表达式规则

`skills/order-mapping/scripts/order_mapping_core/expressions.py:1-232` 是有限表达式语法，不是自然语言模型：

- `:40-167` 只按配置的 connectors、markers、modifier aliases、前后缀连接词拼接有限表达式变体。
- `:169-232` 对每个当前目录名称计算属性签名，要求基础名和显式属性全部相同；若解释、计价规格或最高价不唯一则保持 `ambiguous`，否则再以当前目录 SKU 调用 `match_item`。

### 3.4 Agent `decisions` / `candidate_reviews` 的实际路径

这是本次最重要的边界：**代码支持外部 Agent 结果，但没有内部 Agent。**

#### `decisions`

`workflow.py:203-250` 的 `_decision(item, decision, catalog, unit_rules)`：

- `:203-208` 先用 `match_item` 建立行，再校验 decision 的当前 `catalog_version`；版本不一致即 `stale_decision`。
- `:209-214` 要求理由、`confirmed_by=user|agent`；若为 agent，必须声明 `selection_basis=constraints_then_highest_price`。
- `:215-228` 检查 decision SKU 必须存在于当前目录、品牌和全部约束不得冲突，然后将 `match_basis` 标为 `agent_semantic` 或 `user_decision`。
- `:233-245` 若 decision 携带 `invoice_quantity`，只有 `confirmed_by=user` 才允许覆盖数量；模型不能推测实重或装箱数。否则仍调用 `invoice_quantity` 按原始请求换算。
- `:246-250` 写入数量依据和理由；换算失败仍保持待核。

这里校验的是 `selection_basis` 声明、当前目录存在性与有限属性冲突；它没有独立证明外部 Agent 穷尽了合理候选，或确实在全部等价候选中选择最高价。真实语义审阅及其独立复核仍是必要步骤。

#### `candidate_reviews`

`workflow.py:258-284` 的 `_candidate_review(item, row, review, catalog)`：

- `:258-267` 要求候选审阅绑定当前目录版本和本条原文 UTF-8 SHA-256。
- `:268-279` 要求审阅者是 `agent` 或 `user`，候选编号去重且全部存在于当前目录；任何明确属性冲突都会拒绝。
- `:280-284` 将 `selected=None`、状态设为 `ambiguous/needs_review/unmapped`，保存 `candidate_review` 和 `match_basis=agent_candidate_review`；它只能否决自动选择或提供当前候选池，不能提升 SKU、不能补造数量。

`SKILL.md:15` 对 Agent 语义审阅的要求与上述结构化契约一致；但 `run-messages` 不会调用它们。因此要形成真正的“原文 + Agent 审阅 + 导出”闭环，当前实现必须由外部 Agent 先生成结构化 `run` 输入，再调用 `order_mapping.py run`，或由宿主另行编排这一步。仓库内未发现模型/API/MCP 调用实现。

## 5. 关键缺口与复盘判断

- 文档层已经写出“Agent 应主动完成语义审阅”（`SKILL.md:15`），但该要求没有在 `run-messages` 内形成调用、状态或宿主接口；当前只能由外部 Agent/人工按照结构化 `decisions`、`candidate_reviews` 契约再走 `run`。
- `match_shared` 的条件、别名和最高价选择可以保证一套可复现的规则行为，但不能证明自然语言中的所有品牌、部位、形态、包装、否定和复合约束都已被理解。
- `candidate_reviews` 的代码能验证候选属于当前目录并保留理由，但没有在脚本内部证明候选集合“完整”；候选完整性仍依赖外部 Agent 的语义审阅和业务证据。
- 目录、单位、金额、编号、导出、批注和指纹审计属于确定性代码的强项，应继续由代码约束；开放式商品语义、候选全集、同名近邻排除、复杂指代和真实履约语义不应被当前正则/别名层宣称已解决。
- 因此，当前实现更准确的定位是：**确定性规则执行器 + 可选的外部 Agent 语义结果承接层 + 可审计的订单/财务导出器**，而不是包含 Agent 语义判断的完整主链路。
