# order-mapping 方案复盘与推荐

日期：2026-11-08。状态：**复盘已形成，优化目标仍为 paused，推荐方案待用户评审。**

本文是讨论与评审材料，不是新的实现基线。现有主设计仍为 [设计方案.md](../../设计方案.md)，实施状态以 [task_plan.md](../../task_plan.md) 和 [执行清单.md](../../执行清单.md) 顶部暂停段为准。本次仅审查已保存的代码、知识、输入及结果，新增复盘文档和证据对照；未新增匹配规则、调参或运行映射评测。未经用户恢复意见，不进入 KB20/V7-12。

## 1. 直接判断：工程保护有进展，核心识别效果仍不理想

现有资料足以继续开发和判断路线价值，不需要用户重复补充三站聊天、人工表或目录。部分订单缺少本次实际重量、具体包装或指代对象，这些缺口必须保留；它们不能解释所有商品身份识别问题。

约十小时期间，共享路线在同一历史业务样本上的 SKU 一致数，早期由 **50/132 提升到 80/132**，有实质改善；但是后续多个 KB 版本仍为 **80/132**。后期主要改善了有限表达、事件关系、金额留空与证据保护，没有在这批核心原始样本上继续增加人工 SKU 命中。继续增加规则和重复大批量运行的收益已经不足。

方案的主要偏差是：原设计采用“Agent 理解聊天 + 确定性代码校验与导出”，实际主要验证了“规则解析 + 选择器匹配 + 导出”。**宿主 Agent 的语义审阅没有成为正常执行与验收的必经步骤。** 目前既不能说完整 Agent skill 已验证，也不能仅凭测试数增加或合成局部成绩宣布业务识别达到 95%。

另有一处指标使用需要纠正：缺重量、缺单位造成的是完整计价行覆盖受限，不能把这个上限套到商品身份匹配。建议把身份、数量和计价分开验收；原来的全字段 A/B 继续保留报告，调整方案获认可前不重写旧口径或旧成绩。

### 2.3 为什么不能把 127/132 与 80/132 当成同口径独立准确率

v5 的 `profile-only` 虽未注入逐事件 `decisions`，但加载了**从同一批人工表提炼的公司 SKU 别名字典**，如“里脊+斤→冷鲜小里脊肉”“豆腐+盒→北大荒老豆腐”“牛奶+箱→完达山小枕”。旧脚本还依据模拟清单的来源公司给已解析事件分区，然后将结构化 `items` 送入 `run`。这些内容使历史拟合更容易保持，但不能证明跨公司新订单能力。

KB19 默认共享链路不加载这些旧 profile，运行端从原文获取公司与日期，也不接收评测事件 ID 和来源公司元数据。知识、输入路径和保守边界都变了。因此可以说历史一致数少了 47 条，不能把差值全部归为同等条件下算法退化，更不能以恢复这 47 个历史答案作为唯一优化目标。

本复盘没有发现据以断言 v5 把人工实配重量全部倒灌进识别的证据；问题主要是 SKU 偏好同源拟合与评测辅助分单，不能扩展成未经核实的指控。

证据：[既有证据对照.json](既有证据对照.json)、[159事件版本逐项对照.csv](159事件版本逐项对照.csv)、[v5 回放器](../v5_replay_audit.py#L297)、[当前固定身份结果](../v7/kb19_original_r2/fixed_identity.json)。

## 3. 实际主链与可移植 skill 的偏差

当前原文执行链为：

`run-messages → parse_chat → 规则匹配与控制关系 → process_batch → 订单/财务导出 → 合并财务`。

解析主要依赖正则、有限词表和商品名边界；匹配主要依赖别名、概念选择器、属性冲突和价格排序。它能复现已配置行为，但难以处理开放式同义、地区叫法、复杂否定和未写入语法的新表达。

`SKILL.md` 已要求 Agent 主动审阅品牌、部位、形态、鲜冻、包装等信息。结构化 `run/process_batch` 也已有 `decisions`、`candidate_reviews` 承接接口。然而 `run-messages` 明确拒绝外部传入这两个字段，内部也没有产生 Agent 审阅结果。正常原文 CLI 的批量评测，因而没有执行这层语义判断。

可移植 skill 不要求 Python 自己绑定某家模型 API；宿主 Agent 本来就可以承担语义理解。当前缺的是**把宿主审阅写成常规执行步骤并留下真实执行证据**，不是再引入模型服务、向量库或新平台。

现有代码适合继续保障当前目录与指纹、同记录名称/规格/价格、明确单位换算、Decimal 金额、编号事务、原生 Excel 批注、颜色、台账及财务复读。开放式商品语义与合理候选全集不宜继续主要依赖规则补丁来宣称解决。

详细入口与行号见 [调用链审查.md](调用链审查.md)。已有的结构化接口可以复用；但其兼容与完整源文绑定还需在获准后的短周期试验中验证，不能把“接口存在”当作闭环已完成。

另外，代码对 Agent 的最高价依据目前只校验声明和有限属性冲突，不证明其穷尽了等价候选；知识 SHA 在加载时计算并写入台账，发布前二次核对的是当前目录，未重新读取知识校验。两点均须作为既有能力边界披露。

## 4. 共享知识没有恢复旧表现：代表性原因与风险

KB19 正式文件已有 93 条概念、2 条单位、1 条受限表达规则，字段覆盖齐全；其中 67 条有条件、18 条仅候选、8 条通用。28 条状态仍为历史审阅未前向验证，26 条为局部测试通过待全回归，11 条要求合成回归。规则有证据字段，不表示证据足以支持全部自动选择；部分自然语言冲突条件也尚未全部变成可执行断言。

共享迁移取消了旧公司具体 SKU 默认值，却没有充分用通用采购语义接替；一部分保守退回是合理保护，另一部分是可推广别名、候选区分或语义执行不足。与此同时，少数泛称规则反而用计价便利来决定商品，存在过度自动化风险。不能统一用“更严格所以更好”解释全部变化。

### 会导致准确率下降的具体场景

- **词表外表达与复合句**：新俗称、合理错字、前后置属性或连续输入越出已配置语法，可能漏切、误切或只能召回候选。
- **泛称与近邻商品**：同名不同鲜冻、部位、品种和包装，规则过窄降低覆盖，规则过宽产生错选；按盒/箱计价便利不能解决商品语义。
- **目录更新**：名称、规格、在售项变化使旧选择器失效；重新解析虽能阻止旧价复用，不能自动补齐新商品语义知识。
- **公司与日期上下文不明**：跨公司混排没有文本归属、日期跨段或跨年不明时不能安全分单。公司仅作归属不意味着允许猜测归属。
- **追加、改量、取消和重复**：没有唯一前驱或商品身份不明会使相关事件待核；把普通重复当追加则会多配、多计金额。
- **数量与包装事实缺失**：条/颗/根到重量、箱/袋装量不明限制计价，但不应连带撤销已经确定的商品身份。
- **候选检索与语义全集不同**：候选太窄会漏项，过宽会把仅共享“鲜活”等属性的其他商品带入；“全部台账候选已写批注”不能证明合理候选完整。
- **评测真值混合**：用历史交付替代直接评原文会惩罚正确约束；大量 undefined 及反复消费保留集，会使成绩难以解释。

## 5. 验收口径应怎样纠正

本节是待评审建议，不追溯修改旧分母，不据此重算一个“已达标”结论。全 159 事件总账始终保留，历史 155/132 也继续披露。

| 指标 | 建议定义与用途 | 建议目标/边界 |
|---|---|---|
| 商品自动选中正确率 | 独立裁定满足原文概念、属性、规格及选品层的自动选择数 / 实际自动选择数 | ≥95%；未决强选和额外自动输出计错，不能只评熟悉 SKU。 |
| 可判定身份需求的正确自动选中覆盖率 | 正确自动选择数 / **运行前独立冻结的可判定身份事件集合** | ≥95%，分站/主要正常场景报告；失败后不能改成“不确定”移出分母。 |
| 全量身份正确自动覆盖率 | 同一正确选择数 / 全部输入事件 | 始终报告；全部异常、未输出和未裁定项仍在分母。不能用正常集合成绩替代此值。 |
| 原数量/单位保留与可证换算 | 原文值保持、换算正确、应待核的处置分别统计 | 原文保留100%；不推实重，不借人工实配量提高覆盖。 |
| 异常业务处置 | 原文、来源、数量单位、合理候选、原因、颜色、原生批注与空金额 | 应全部通过；候选语义全集未裁定时，完整业务正确率 C 仍为 unknown。 |
| 完整可计价行覆盖 | 全字段已证正确、可安全计价的活动事件 / 全部输入事件 | 独立披露事实限制与当前完成数，不等同商品识别95%。 |
| 旧全字段 A/B/C | 保留原合同定义与已保存结果 | 不删除；候选语义全集及独立全字段预期不足时，不能强给正式成绩。 |

“可判定”不能定义成执行器愿意匹配，也不能定义成已命中的条目。应由运行前的独立审阅，根据原文、当前目录及正式知识冻结：明确可判、商品已知但数量待核、身份歧义、目录缺项、关系不明、评测未裁定；允许裁定等价候选层而非只认人工表单一 SKU。后续纠正预期须另版保留证据，原结果不覆盖。

已经逐项证实的 17 条硬事实缺口，使“全 159 条完整可计价自动行”的乐观上界为 **142/159=89.31%**，还假设其余全部成功。这是计价覆盖的宽松上界，**不是商品身份可达上限，也不是当前实现成绩**。当前仍有其他语义、关系及候选问题，不能承诺已能完成剩余142条。

17 条包括：松北的鲤鱼3条、血肠1根、白菜2颗、厚皮鸡蛋1筐、窝瓜1个、甘蓝3颗、罗马生菜1颗、白萝卜1根、“这样的刷锅5个”；星月的饺子皮300个、孜然粉2、猪肘去毛5个、萝卜丁咸菜大袋的；学院路的白菜3颗、鲤鱼5条收拾好、小白菜3颗、生猪手撩毛8个。缺口及当前空金额逐项见 [硬事实复核](../v7/kb19_source_fact_recheck.json)。其中有些商品身份可确定，有些同时缺品种、包装或指代；不能将17条统一标成无法识别。

因此，不应继续用“含大量应人工事件的全字段 B 也必须95%”作为每轮补规则的单一驱动力。应保留旧全量成绩，先验证商品识别路线能否在预先可判定需求上同时取得高正确率与覆盖。

## 6. 合成评测有价值，但独立性和结论必须收敛

已有历史随机回归 540 次 CLI，覆盖 180 case × 3 模式。6108、6109、6112 各 seed 的拆分、重排、跨站场景分别包含完整159事件；来源、公司、日期、原数量和单位漂移为0，财务机械错误为0。这证明已配置解析/导出在这些变形中的稳定性，不增加159条真实业务的样本量。

使用同一旧 oracle 的 shared 诊断，KB17 与 KB19 均为自动828、自动符合旧预期439、全量1551个变体事件，保守诊断 A=53.02%、B=28.30%。463条预期为 undefined，其中自动行298条。它们不是具有完整独立真值的新订单准确率；旧 C 数字也不作为正式 C，正式状态仍为 unknown。

历史报告的 `invoice_quantity` 诊断每模式增加12条，共36条，逐行比对均是原量/单位不变、事件前后都 pending、金额前后都为空；变化是计价量从1或2改成 null。每 seed 为重排“小白菜1斤”1条、改量初始1条、普通重复2条。它反映当前安全合同与旧评分预期不兼容，不能直接当成原始数量解析回归。此处以复盘逐行对照 JSON 为准。

保存核对另发现：历史运行目录的 `summary.json` 与暂停检查点SHA不同，原始 `replay_audit.json` 未变化。协作审计方确认检查点后补写了摘要JSON及Markdown，未重跑runner；其比较以 `(mode, case_id, source_event_id)` 作字典键，使同case下来源ID为空的多行被覆盖。当前摘要的局部归因只列了每模式6条，遗漏另6条，不能作上述增量数量的权威来源。本次不覆盖暂停检查点或旧摘要；发现时两份摘要另存快照，变更指纹及该冲突保留在交付检查中，复盘采用原始回放的逐行对照。

| 已保存挑战 | shared结果 | 有效结论与限制 |
|---|---|---|
| 9201/9202/9291 current_r4 | A=100%，全量60/96=62.5%；正常60/72=83.33% | 正常中12条身份条件不足仍留分母；四公司各15/24。r2的56/96到60/96属于已见问题修复，不是新盲测提升。 |

这些测试可保留为解析与工程保护网。下一轮需要提高**每次试验的辨别力**：相同原文输入、不同识别路线、独立冻结裁定和具体错误归因；不应再用相同原事件的大量变体或漂亮局部百分比代替业务进步。

## 7. 推荐路线：宿主 Agent 语义审阅，代码保证事实与表格

| 路线 | 能复用什么 | 主要问题 | 建议 |
|---|---|---|---|
| 继续逐条增加别名/正则/选择器 | 现有解析器和知识文件 | 有限语法维护成本上升；核心历史样本后期已停滞，泛称仍缺裁定 | 保留必要修错，暂停作为主优化路线。 |
| 宿主 Agent 读原文、共享知识和当前目录，输出本批语义判断，代码校验/导出 | 现有技能说明、目录、知识、parse、run、decisions、candidate_reviews、金额/Excel/财务 | 必须实测语义步骤、绑定原文和目录，约束模型不编造数量；结果仍可能不达95% | **推荐先做一次有上限的试验。** |
| 纯 Agent 直接生成最终 Excel | 文本指令 | 编号、目录一致性、金额和原生批注难稳定复核 | 不作为正式主链。 |
| 新建独立平台、检索服务或绑定模型API | 部分业务模型 | 超出当前问题所需，增加部署、外传与兼容成本，未先证明识别增益 | 当前不做。 |

推荐流程为：**原始消息 → 保留来源的事件建议 → 宿主 Agent 检索共享知识与当前目录、审阅候选 → 本批决策或异常 → 确定性数量/金额校验 → 同台账订单与财务导出 → 保存后复读**。

Agent 可以修正语义切分与候选判断，但输出必须对应本次原文范围；内部事件标识只能由本次输入生成，不能用评测来源 ID。决策须绑定原文 SHA、当前目录、知识版本、具体理由和约束检查；候选集要保留纳入/排除理由。当前接口已有部分目录/原文校验，其余绑定属于待验证的实施项，本文不声称已实现。

共享知识继续以概念、同义、属性、候选规则和证据随 skill 交付。历史替代和实配调整只作历史解释；正式公司特殊约定保留单独证据，目前为空。最高价必须在满足原文且最接近需求的等价候选层内比较，计价可算性不能反过来替商品需求作选择。

继续复用目录更新、单位、Decimal、编号、批注、台账及财务组件；停止无差别扩跑、以历史 SKU 恢复作为唯一目标，以及为了计价便利选择未证实商品的做法。对于有明确公司/日期的普通批次，先验证最短完整流程，不在本轮复盘中搭建新框架。

千问办公、WorkBuddy至少需要读取UTF-8文本/JSON与当前目录、执行Python及openpyxl或提供等价Excel操作、保留目录状态、写原生批注并复读工作簿。当前两种宿主均未实测。宿主缺少原生批注或执行能力时，应标能力不足，不能把CSV或只在会话解释异常当作完成同一交付合同。

## 8. 待评审的短周期计划：一次试验后停下看证据

本节**仅为下一轮提案，本次不执行**。目标是证伪或支持推荐路线，不保证一次达到95%，也不自动进入下一版知识扩张。

硬上限建议为 **90分钟、两种执行路线、每路线最多20个批次**。使用同一冻结输入：原始159事件做历史诊断；另保留12条信息完整、目录支持的新表达和6条异常挑战，合计177事件。新表达选择6个未用于本轮规则提炼的目录概念，覆盖三站与一个新公司；重复变体不算新真实样本。仅独立构造方可见预期，执行方只见原文、正常公司/日期配置、目录和正式知识。

| 时间上限 | 工作 | 必须留下的结果 |
|---|---|---|
| 0–20分钟 | 独立审阅并冻结159事件的身份可判定分类、历史差异；冻结18条挑战、当前知识与目录 | 固定总账、预期及SHA，记录未裁定项。时间内裁定不完则停止，不草率填真值。 |
| 20–50分钟 | 对同一输入运行规则基线与实际宿主Agent语义路径；分别存本批决策 | 正常输入隔离证据、语义理由、候选、原文span和两组输出。不得在执行端读取答案。 |
| 50–75分钟 | 独立核对身份、原量单位、属性约束、异常；复读订单与财务 | 每条差异归因、正确率/覆盖、分公司/场景和硬约束错误。 |
| 75–90分钟 | 汇总路线价值与失败，原件/SHA检查，停下报告 | 同分母对照、剩余未决和可复现证据。无论结果如何都不自动扩跑。 |

试验中任何品牌、物种、部位、形态或包装硬约束错选、编造原量、评测泄漏、原件变化，都判本轮不通过；保留失败证据，不能靠追加规则重跑后只报最后成绩。冻结后发现预期错误，另版纠正并保留首轮，不计作首次独立通过。

业务验收仍需独立身份自动正确率和预先可判定需求覆盖均≥95%，分站与主要场景披露，异常合同全部通过。全177与原159的覆盖也必须报告。若覆盖提高至少15个百分点且没有新增硬约束错误，可证明路线有继续研究价值，**仍不等于达标**；若没有明显增益、仍靠无证据猜测、或无法在上限内形成独立真值，就结束本轮并记录不成立的假设，不继续无上限补规则。

18条挑战的样本量只能检验路线和具体失败，无法建立未来真实订单95%的统计保证。最终还需把历史回归、保留合成和真实新增订单分开验收；真实新增订单及其他宿主测试目前均未执行。
